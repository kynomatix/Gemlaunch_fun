C-2: Sell Function Fee Calculation Inconsistency
Location: BondingCurvePool.sol - sellTokens()
Issue: Fee calculation logic differs from buy, creating asymmetry:
solidity// Buy: Fees deducted from INPUT (msg.value)
uint256 totalFees = msg.value * 150 / 10000;
uint256 tradeAmount = msg.value - totalFees;
uint256 tokensOut = quoteBuy(tradeAmount);

// Sell: Fees deducted from OUTPUT (kasOut)
uint256 kasOut = quoteSell(tokenAmount);
uint256 totalFees = kasOut * 150 / 10000;
uint256 netKasOut = kasOut - totalFees;
Problem: This creates asymmetric round-trip pricing:
Example:
1. User buys with 100 KAS
   - Fees: 1.5 KAS deducted
   - Trade amount: 98.5 KAS enters reserves
   - Receives: X tokens (based on 98.5 KAS)

2. User immediately sells X tokens
   - quoteSell(X) = 98.5 KAS (from reserve)
   - Fees: 98.5 * 0.015 = 1.4775 KAS
   - User receives: 97.0225 KAS
   
Total loss: 100 - 97.0225 = 2.9775 KAS (2.98%)
BUT only 1.5% + 1.5% = 3% fees expected!
The math doesn't work: If fees are 1.5% on both sides, round-trip should lose ~2.97%, but the asymmetry causes confusion.
Root Cause:

Buy: Fee on INPUT (before AMM)
Sell: Fee on OUTPUT (after AMM)
AMM invariant violated differently on each side

Correct Implementation:
solidity// CONSISTENT APPROACH: Fee on INPUT for both

// Buy (current - correct):
uint256 feesOnInput = msg.value * 150 / 10000;
uint256 tradeAmount = msg.value - feesOnInput;
uint256 tokensOut = quoteBuy(tradeAmount);

// Sell (needs fix):
uint256 feesOnInput = tokenAmount * 150 / 10000; // Fee in TOKENS
uint256 tradeTokens = tokenAmount - feesOnInput;
uint256 kasOut = quoteSell(tradeTokens);
// User receives full kasOut (no second fee deduction)

// OR: Fee on OUTPUT for both (but update buy too)
Alternative (simpler): Use Uniswap V2 pattern - fee INSIDE the AMM:
solidityfunction quoteBuy(uint256 kasIn) public view returns (uint256 tokensOut) {
    uint256 kasInWithFee = kasIn * 9850 / 10000; // 1.5% fee
    uint256 k = virtualTokenReserve * virtualKasReserve;
    uint256 newKasReserve = virtualKasReserve + kasInWithFee;
    tokensOut = virtualTokenReserve - (k / newKasReserve);
}
Risk: CRITICAL - Incorrect fee accounting, value leakage

C-3: Graduation Threshold Check Timing Issue
Location: BondingCurvePool.sol - buyTokens()
Issue: Graduation check happens BEFORE reserve update:
solidity// Calculate tokens
uint256 tokensOut = quoteBuy(tradeAmount);

// Check graduation BEFORE updating reserves
bool willGraduate = !graduated && (virtualKasReserve + tradeAmount >= GRADUATION_THRESHOLD);

if (willGraduate) {
    graduating = true; // Lock set
}

// Update reserves AFTER check
virtualKasReserve += tradeAmount;
Problem: The check uses virtualKasReserve + tradeAmount, but:

If current reserve is 74 KAS
User buys with 1 KAS (trade amount after fees ~0.985 KAS)
Check: 74 + 0.985 = 74.985 < 75, no graduation
Reserve updated to 74.985 KAS
Next tiny buy triggers graduation, but pool doesn't have full 75 KAS!

Correct Logic:
solidity// Update reserves FIRST
virtualKasReserve += tradeAmount;
virtualTokenReserve -= tokensOut;

// Check AFTER update (use actual new state)
bool shouldGraduate = !graduated && !graduating && virtualKasReserve >= GRADUATION_THRESHOLD;

if (shouldGraduate) {
    graduating = true;
    // ... graduation logic
}
Why This Matters:
Current code checks FUTURE state but that future state might not meet threshold after fees. The reserve should be updated FIRST (CEI pattern), then checked.
Risk: CRITICAL - Graduation triggered with insufficient reserves

C-4: _executeGraduation() Reserve Split Logic Error
Location: BondingCurvePool.sol - _executeGraduation()
Issue: The 75/25 split calculation is backwards:
solidity// Snapshot reserves for LP creation
uint256 kasForLP = virtualKasReserve;
uint256 tokensForLP = virtualTokenReserve;

// Calculate 75/25 split for LP
uint256 curveKas = kasForLP * 75 / 100;  // ??? This stays in curve?
uint256 lpKas = kasForLP * 25 / 100;     // Only 25% to LP?
Conceptual Error:

virtualKasReserve = all KAS raised from trading (should be ~75 KAS at graduation)
virtualTokenReserve = remaining tokens in curve (was 75% of supply, now partially sold)

The 75/25 split refers to INITIAL SUPPLY, not current reserves!
Initial Token Supply Distribution:
- 75% to bonding curve (virtualTokenReserve starts here)
- 25% reserved for LP (NOT in virtualTokenReserve)

At graduation:
- virtualKasReserve = all KAS raised (~75 KAS)
- virtualTokenReserve = unsold tokens from the 75%
- LP should get: 25% of TOTAL SUPPLY (not 25% of current reserves)
Correct Implementation:
solidityfunction _executeGraduation() internal {
    require(graduating && !graduated, "Invalid state");
    graduated = true;
    
    // ALL KAS in virtual reserve goes to LP
    uint256 kasForLP = virtualKasReserve;
    
    // LP gets the 25% reserved tokens (NOT from virtualTokenReserve)
    // These should be separately minted/held
    uint256 lpTokens = totalSupply() * LP_SUPPLY_PCT / 100;
    
    // Burn remaining curve tokens (unsold from 75%)
    uint256 unsoldCurveTokens = virtualTokenReserve;
    if (unsoldCurveTokens > 0) {
        _burn(address(this), unsoldCurveTokens);
    }
    
    // Create LP with: kasForLP + lpTokens
    IGraduationController(graduationController).graduateToken{value: kasForLP}(
        address(this),
        lpTokens,
        kasForLP
    );
}
Alternative (if 25% already in contract):
solidity// During construction:
uint256 curveTokens = totalSupply * 75 / 100;
uint256 lpTokens = totalSupply * 25 / 100;

virtualTokenReserve = curveTokens; // Only 75% in curve
// lpTokens held separately, not in virtualTokenReserve

// At graduation:
uint256 kasForLP = virtualKasReserve; // All KAS
uint256 tokensForLP = lpTokens; // The reserved 25%
Risk: CRITICAL - Wrong LP ratio, economic model broken

H-2: Transfer Cooldown Can Be Bypassed
Location: _transfer() override
Issue: Cooldown exempts transfers FROM pool:
solidityif (from != address(this)) { // Exempt buys from pool
    require(
        block.timestamp >= lastTransferTime[to] + TRANSFER_COOLDOWN,
        "Transfer cooldown active"
    );
}
Bypass:

User buys tokens (from = pool, cooldown NOT checked)
Immediately transfers to another wallet (cooldown checked, passes if first time)
Immediately transfers to another wallet (cooldown checked, passes if first time)
Repeat with infinite wallets

Better Implementation:
solidity// Track BOTH sender and receiver
mapping(address => uint256) public lastTransferTime;

function _transfer(address from, address to, uint256 amount) internal override {
    if (!graduated && from != address(this) && to != address(this)) {
        // Check sender cooldown
        require(
            block.timestamp >= lastTransferTime[from] + TRANSFER_COOLDOWN,
            "Sender cooldown active"
        );
        
        // Check receiver cooldown  
        require(
            block.timestamp >= lastTransferTime[to] + TRANSFER_COOLDOWN,
            "Receiver cooldown active"
        );
        
        lastTransferTime[from] = block.timestamp;
        lastTransferTime[to] = block.timestamp;
    }
    
    // Wallet cap check...
    super._transfer(from, to, amount);
}
Risk: HIGH - Cooldown mechanism easily bypassed

H-5: Emergency Fee Rescue Has No Timelock
Location: rescueStuckCreatorFees()
Issue: Marked as "admin + timelock" but no timelock shown:
solidityfunction rescueStuckCreatorFees(address newRecipient) external onlyAdmin afterTimelock {
    // Verify creator actually cannot receive
    (bool canReceive, ) = payable(creator).call{value: 0}("");
    require(!canReceive, "Creator can receive");
    
    // Transfer to new recipient
}
Problems:

No afterTimelock modifier implementation shown
onlyAdmin not defined (should be AccessControl role)
Creator verification is weak (0 value call doesn't prove anything)

Better Implementation:
solidityimport "@openzeppelin/contracts/access/AccessControl.sol";

bytes32 public constant ADMIN_ROLE = keccak256("ADMIN_ROLE");
uint256 public constant RESCUE_TIMELOCK = 7 days;

struct FeeRescueProposal {
    address newRecipient;
    uint256 proposalTime;
    bool executed;
}

mapping(address => FeeRescueProposal) public rescueProposals;

function proposeFeeRescue(address newRecipient) external onlyRole(ADMIN_ROLE) {
    require(accumulatedCreatorFees > 0, "No fees to rescue");
    
    rescueProposals[creator] = FeeRescueProposal({
        newRecipient: newRecipient,
        proposalTime: block.timestamp,
        executed: false
    });
    
    emit FeeRescueProposed(creator, newRecipient, block.timestamp + RESCUE_TIMELOCK);
}

function executeFeeRescue() external onlyRole(ADMIN_ROLE) {
    FeeRescueProposal storage proposal = rescueProposals[creator];
    require(!proposal.executed, "Already executed");
    require(block.timestamp >= proposal.proposalTime + RESCUE_TIMELOCK, "Timelock active");
    
    // More robust check that creator cannot receive
    (bool canReceive, ) = payable(creator).call{value: 1 wei}("");
    if (canReceive) {
        revert("Creator can receive - rescue not needed");
    }
    
    uint256 amount = accumulatedCreatorFees;
    accumulatedCreatorFees = 0;
    proposal.executed = true;
    
    _safeSend(proposal.newRecipient, amount);
    emit FeeRescueExecuted(creator, proposal.newRecipient, amount);
}
Risk: HIGH - Admin can rug creator fees without delay

H-6: No Circuit Breaker for Rapid Price Movements
Location: Missing from implementation
Issue: Documentation mentions "Circuit breaker for price spikes" but not implemented:
solidity// No price change detection
// No automatic pause on extreme moves
// No maximum price impact per trade
Attack Scenario:
1. Whale dumps 50 KAS in one trade
2. Price crashes 90%
3. Bot buys at bottom
4. Bot sells back for profit
5. Regular users suffer losses
Implementation:
solidityuint256 public lastTradePrice;
uint256 public constant MAX_PRICE_CHANGE_BPS = 2000; // 20% max per trade

function _checkCircuitBreaker(uint256 newPrice) internal {
    if (lastTradePrice > 0) {
        uint256 priceChange = newPrice > lastTradePrice
            ? ((newPrice - lastTradePrice) * 10000) / lastTradePrice
            : ((lastTradePrice - newPrice) * 10000) / lastTradePrice;
        
        if (priceChange > MAX_PRICE_CHANGE_BPS) {
            _pause();
            emit CircuitBreakerTriggered(lastTradePrice, newPrice, priceChange);
            revert("Price movement too large - circuit breaker triggered");
        }
    }
    lastTradePrice = newPrice;
}

function buyTokens(...) external payable {
    uint256 newPrice = getCurrentPrice();
    _checkCircuitBreaker(newPrice);
    // ... rest of buy logic
}
Risk: HIGH - Flash crash vulnerability
