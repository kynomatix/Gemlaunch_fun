# Contract-by-contract findings

## BondingCurvePool.sol

### Critical - curve math is internally inconsistent and can underflow

* `quoteBuy` and `quoteSell` compute using `remainingTokens` and `address(this).balance` with midpoint heuristics. The units alias as tokens per ETH then reinterpreted as ETH refunds in sell. This is error-prone and breaks conservation expectations in round-trips. You will leak value depending on trade ordering and fee skim.

* `quoteSell` uses `(address(this).balance - (ethAmount / 2))` in a denominator. If a user sells a large amount relative to reserves, this can go to zero or underflow. Even before zero, price explodes and slippage checks may fail in non-intuitive ways.

* You floor to `0.01 ether` when ETH balance is small. That creates a discontinuity that sophisticated bots can exploit at the moment the floor flips.

**Fix**

Pick a principled curve and stick to it. Two sane choices that are easy to reason about and fuzz:

* Virtual-reserve CPMM like pump.fun v2 style:

```
P(x,y) with virtual reserves x0,y0
Buy Δy for input Δx: invariant (x + x0) * (y - Δy + y0) = (x + Δx + x0) * (y + y0)
```

* Or a linear bonding curve where price is a function of outstanding supply, and you integrate to get cost. If you prefer linear, implement the integral form with exact rounding rules and no midpoint hacks.

Whichever you choose, encode it once, document the invariant, and write Foundry properties:

* Invariant A: roundTrip(Δx) returns within 1 percent after fees.
* Invariant B: reserves are never negative.
* Invariant C: marginal price is monotone increasing with outstanding supply for buys, decreasing for sells.

### Critical - fee accounting breaks conservation and creates drift

* In buy, you compute tokens from `tradeAmount = msg.value - totalFees` which is reasonable, but you increment `totalRaised += tradeAmount` while in sell you decrement `totalRaised -= kasRefund` where `kasRefund` is pre-fee. This makes totalRaised non-symmetric and can even go negative after sequences of buys and sells.

**Fix**

Track two independent meters:

* `grossInBase` - sum of all pre-fee input KAS that hit the curve.
* `netReservesBase` - actual base held by the contract for curve liquidity.

On buy:

* fees skimmed to treasury and fee pot, `grossInBase += msg.value`, `netReservesBase += tradeAmount`.

On sell:

* pay `userRefund` to trader, skim fees, and `grossInBase` is unchanged, `netReservesBase -= kasRefund`.

Use `netReservesBase` and `tokenReserves` only for curve pricing. Never use gross meters in price formulas.

### High - native asset send uses transfer

* `payable(treasury).transfer(platformFee)` and others. `transfer` uses 2300 gas and can brick if recipient is a smart wallet with non-trivial receiver logic.

**Fix**

Use low-level call with return checks:

```solidity
(bool ok, ) = treasury.call{value: platformFee}("");
require(ok, "treasury send failed");
```

Wrap this behind an internal `_safeSend(address,uint256)` helper and reuse.

### High - missing slippage and deadline checks in the examples

You mention slippage and deadlines, but the function signatures do not accept `minTokensOut` or `deadline`. Without those, a user cannot protect against MEV.

**Fix**

```solidity
function buyTokens(uint256 minOut, uint256 deadline) external payable nonReentrant {
  require(block.timestamp <= deadline, "expired");
  uint256 tokens = _quoteBuyAfterFees(msg.value);
  require(tokens >= minOut, "slippage");
  ...
}
```

Mirror on sell with `minRefund`.

### High - wallet cap computed on `totalSupply()`

If `totalSupply()` includes tokens reserved for LP but still held by the contract, your 10 percent cap becomes easier or harder based on the initial supply scheme. The cap should be based on circulating supply, not total supply.

**Fix**

Define `circulating = totalSupply() - balanceOf(address(this)) - lockedForLP`. Cap against `circulating`.

### Medium - creator fees trapped and push-paid at graduation

* Accumulating native KAS and pushing at graduation increases attack surface. If the creator is a contract with a revert-prone receive hook, graduation bricks. If the creator disappears, you do not want to block graduation.

**Fix**

Move to a pull model. Record `creatorFeesAccrued` and let the creator call `withdrawCreatorFees()` any time. Graduation should not depend on a successful payout. If you want the big payout at graduation for optics, do a best effort call and swallow failure while emitting an event.

### Medium - cooldown and rate limits underspecified

You reference rate limiting and circuit breakers but no code. Without a per-block or per-interval cap across the pool, a bot can still drain inventory at a beneficial marginal price, subject to slippage.

**Fix**

* Add a per-pool `maxBuyBasePerBlock` and `maxSellTokenPerBlock`.
* Track `lastBlockVolumeBase` and `lastBlockVolumeToken`.
* Enforce caps.

### Low - event completeness

Emit full context for analytics. Include base before, base after, token before, token after, and fee fields in `TokensPurchased` and `TokensSold`. This makes reconciliation and watchdogs easier.

## GraduationController.sol

### Critical - graduation sequence is not atomic and is front-runnable

* You verify eligibility, then fetch amounts, then transfer liquidity, then add LP. There are multiple external calls and no lock over the pool state. A large trade can happen between checks and adds, which opens a window to manipulate price or drain reserves before LP add, then you lock curve at the end. Also paying creator first allows balance changes before LP add.

**Fix**

* Add a one-shot mutex in the pool: `lockForGraduation()` callable only by the controller. It flips a `graduating` flag and freezes buy and sell instantly.
* Once frozen, snapshot `tokenReserves` and `baseReserves` used for LP add, then move assets.
* Add LP in a single tx.
* Mark `graduated = true`, permanently.
* Emit `Graduated` with the exact snapshots.

Also add a non-reentrant guard on the controller itself.

### High - ambiguous ownership of LP tokens

* You say burn or send to treasury. Decide one policy. Burning LP is the simplest credible commitment. If you need protocol-owned liquidity, send to a timelocked multisig and publish the policy.

**Fix**

* If burning: route liquidity tokens to `0x0000...dead` directly in the router call if supported, or transfer and burn right away.
* If treasury: require a governance timelock and an event with an immutable freeze period.

### Medium - router assumptions

* Interface assumes `swapExactETHForTokens` and `addLiquidityETH` style of a Uniswap v2 router, and assumes a wrapped KAS `WKAS`. Confirm Kaspa Finance router signature matches, and pin address constants per network. If not, you must adapt the calls.

**Fix**

* Put a RouterConfig registry on-chain that stores per-network router addresses and WKAS, set at deploy, and test against a stub in Foundry. Add a smoke test that does a full LP add on testnet with tiny amounts.

## Treasury/VestingVault.sol

### High - TWAP buyback naive and will leak value

* Blind `swapExactETHForTokens` without any oracle, path checks, or limit prices is a cash drain if liquidity is thin or path is malicious. Also you burn all at once which removes the ability to stream burns.

**Fix**

* Read a time-based oracle from the DEX if available, or compute your own median price from recent trades and enforce a max deviation.
* Use `swapExactETHForTokensSupportingFeeOnTransferTokens` only if you know tokens can be fee-on-transfer.
* Spread buybacks across ticks with a keeper that randomizes exact call times to reduce predictability.
* Accrue purchased GEM in treasury and burn via a separate function with its own schedule. This allows governance to pause burning in emergencies.

### Medium - distributeFees drains full balance

* `distributeFees` splits the entire balance on each call. If someone calls it after a small fee arrives you trigger many tiny sends.

**Fix**

* Track accumulators and distribute only when `balance >= minDistribution`.
* Add a circuit breaker. If any send fails, revert and keep the funds.

### Low - vesting schedule type not shown

* The struct and cliff rules are missing. Vesting mistakes are common.

**Fix**

* Use OpenZeppelin VestingWallet or port its logic.
* For KAS native, implement a unit-tested linear release function with cliffs. Add `preview` functions to enable UI.

# Economic and game-theory review

* Creator fee accrues on both buys and sells. That creates a sell tax that can deter liquidity testing. If you must keep it, consider accrue-on-buys only until graduation to reduce tax friction.

* Wallet cap at 10 percent is fine for soft decentralization. Bots can sybil across wallets. Add a per-block volume guard as noted earlier.

* Graduation threshold is a single scalar in base units. On volatile days this invites threshold sniping. Consider a two-condition rule: base raised threshold plus minimum unique holder count or minimum number of buys across distinct addresses. This improves fairness and reduces a single whale’s ability to force list timing.

* At graduation, ratio of base to token handed to LP should match the spot price from the curve to avoid instant price jumps. Compute exact spot and pass amounts that align to it within a tolerance.

# Access control and upgradeability

* Only the Factory should be upgradeable, and only for deploying new versions. Pools should be immutable once created. GraduationController can be upgradeable with a proxy but design with a kill switch that freezes upgrades unless governance timelock triggers them.

* Roles: ADMIN for param edits through timelock, GUARDIAN limited to pausing, PAUSER can pause only the specific pool. Multi-sig should own the timelock, not the contracts directly.

# Reentrancy and CEI checklist

* Use ReentrancyGuard on all external state mutating entry points.
* Always update state before external calls.
* All native sends via call after state changes.
* For ERC20 interactions, use SafeTransferLib or OpenZeppelin SafeERC20.
