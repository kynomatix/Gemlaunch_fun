## 🔴 **CRITICAL ISSUES** (Must Fix Before Deployment)

### C-1: VestingManager Has No Access Control
**Severity**: CRITICAL - Security vulnerability + gas griefing  
**Location**: `VestingManager.sol` line 15

**The Problem**:
```solidity
function deployVestingContracts(...) external returns (VestingContracts memory result) {
    // NO ACCESS CONTROL!
    // Anyone can call this function
}
```

Anyone can call `deployVestingContracts()` and deploy vesting contracts. While these contracts are harmless if not funded, this allows:
1. **Gas griefing**: Attacker deploys thousands of empty vesting contracts
2. **Confusion**: Multiple vesting contracts exist for same parameters
3. **Wasted resources**: Unnecessary contract deployments

**Fix**:
```solidity
contract VestingManager {
    address public immutable factory;
    
    constructor(address _factory) {
        require(_factory != address(0), "Invalid factory");
        factory = _factory;
    }
    
    function deployVestingContracts(...) external returns (VestingContracts memory result) {
        require(msg.sender == factory, "Only factory can deploy");
        // ... rest of function
    }
}
```

**Also update TokenFactory constructor**:
```solidity
vestingManager = new VestingManager(address(this));
```

### C-2: Missing Balance Verification in finalizeVestingSetup()
**Severity**: CRITICAL - Accounting bug could leave tokens stuck  
**Location**: `BondingCurvePool.sol` line 190

**The Problem**:
The spec (CL-1 fix) says:
> Add balance verification in finalizeVestingSetup()

But the implemented code is missing this check:
```solidity
function finalizeVestingSetup() external {
    require(msg.sender == factory, "Only factory");
    require(!vestingInitialized, "Already finalized");
    
    vestingInitialized = true;
    reserveDistributed = true;
    
    // ❌ MISSING: Balance verification!
    
    emit VestingFinalized(block.timestamp);
}
```

**Why This Matters**:
If vesting transfers fail partially or rounding errors occur, the contract could have incorrect token distribution, but finalizeVestingSetup() succeeds anyway, locking the state.

**Fix** (from spec):
```solidity
function finalizeVestingSetup() external {
    require(msg.sender == factory, "Only factory");
    require(!vestingInitialized, "Already finalized");
    
    vestingInitialized = true;
    reserveDistributed = true;
    
    // ✅ CRITICAL: Verify expected balance after vesting transfers
    uint256 lpSupply = totalSupply() * 25 / 100;
    uint256 expectedBalance = virtualTokenReserve + lpSupply;
    require(
        balanceOf(address(this)) == expectedBalance,
        "Vesting transfer accounting mismatch"
    );
    
    emit VestingFinalized(block.timestamp);
}
```

### C-3: Missing Allocation Validation in TokenFactory
**Severity**: HIGH - Wasted gas + poor UX  
**Location**: `TokenFactory.sol` line 112

**The Problem**:
TokenFactory doesn't validate allocations BEFORE deploying the pool. It relies on VestingManager to validate:

```solidity
function createToken(...) external {
    // Validates name, symbol, supply...
    
    // ❌ NO VALIDATION of vesting allocations here!
    
    // Deploys pool (expensive!)
    BondingCurvePool pool = new BondingCurvePool(...);
    
    // Only NOW does VestingManager check allocations
    VestingManager.VestingContracts memory vesting = VestingManager(vestingManager).deployVestingContracts(...);
    // If allocations invalid (e.g., sum to 110), transaction reverts HERE
    // But pool is already deployed, gas wasted!
}
```

**Fix**:
```solidity
function createToken(...) external nonReentrant whenNotPaused returns (...) {
    // Existing validations...
    require(totalSupply <= 1_000_000_000 * 10**18, "Supply high");
    
    // ✅ ADD: Validate vesting parameters BEFORE deploying pool
    if (reservedPercentage > 0) {
        require(reservedPercentage <= 25, "Vesting exceeds 25%");
        uint256 totalAllocations = airdropsAllocation + marketingAllocation + teamAllocation;
        require(totalAllocations == 100, "Allocations must sum to exactly 100%");
        require(totalAllocations > 0, "Must have at least one allocation");
    }
    
    // NOW deploy pool (only if validations pass)
    BondingCurvePool pool = new BondingCurvePool(...);
    // ... rest
}
```

## 🟠 **HIGH SEVERITY ISSUES**

### H-1: No Way to Query Vesting Contract Addresses from Pool
**Severity**: HIGH - UX limitation  
**Location**: `BondingCurvePool.sol` - missing storage

**The Problem**:
If someone has a pool address, there's no way to find the associated vesting contracts on-chain. The only way is:
1. Query the TokenFactory event logs
2. Ask the backend database

But smart contracts can't access event logs, and wallets may want to query directly.

**Fix - Add Storage**:
```solidity
// Add to BondingCurvePool state variables
address public airdropVestingContract;
address public marketingVestingContract;
address public teamVestingContract;

// Modify transferReserveToVesting to track contract type
enum VestingType { Airdrop, Marketing, Team }

function transferReserveToVesting(
    address vestingContract,
    uint256 amount,
    VestingType vestingType
) external nonReentrant {
    require(msg.sender == factory, "Only factory");
    require(!vestingInitialized, "Already finalized");
    require(vestingContract != address(this), "Cannot vest to self");
    
    // Track vesting contract
    if (vestingType == VestingType.Airdrop) {
        airdropVestingContract = vestingContract;
    } else if (vestingType == VestingType.Marketing) {
        marketingVestingContract = vestingContract;
    } else {
        teamVestingContract = vestingContract;
    }
    
    isVestingContract[vestingContract] = true;
    _transfer(address(this), vestingContract, amount);
    
    emit VestingTransfer(vestingContract, amount, block.timestamp);
}

// Add getter
function getVestingContracts() external view returns (
    address airdrop,
    address marketing,
    address team
) {
    return (airdropVestingContract, marketingVestingContract, teamVestingContract);
}
```

**Also update TokenFactory calls**:
```solidity
pool.transferReserveToVesting(
    airdropVestingAddress,
    vesting.airdropTokens,
    BondingCurvePool.VestingType.Airdrop
);
```

### H-2: getReserveStatus() Returns Misleading Data for PRO Tokens
**Severity**: MEDIUM - Confusing function behavior  
**Location**: `BondingCurvePool.sol` line 461

**The Problem**:
```solidity
function getReserveStatus() external view returns (
    bool distributed,
    uint256 availableReserve,
    uint256 totalReserve
) {
    distributed = reserveDistributed;
    totalReserve = totalSupply() * LP_SUPPLY_PCT / 100; // ❌ Always returns 25%
    
    if (!graduated && !graduating) {
        availableReserve = balanceOf(address(this)) - virtualTokenReserve;
    } else {
        availableReserve = 0;
    }
}
```

For PRO tokens, this function returns:
- `totalReserve`: 25% (LP supply)
- But PRO tokens have 0-25% VESTING (different from LP)

The function is only meant for BASIC tokens (since PRO tokens block `distributeReserve()`), but this isn't clear.

**Fix**:
```solidity
function getReserveStatus() external view returns (
    bool distributed,
    uint256 availableReserve,
    uint256 totalReserve
) {
    require(reservedPercentage == 0, "PRO tokens use vesting contracts");
    
    distributed = reserveDistributed;
    totalReserve = totalSupply() * LP_SUPPLY_PCT / 100;
    
    if (!graduated && !graduating) {
        availableReserve = balanceOf(address(this)) - virtualTokenReserve;
    } else {
        availableReserve = 0;
    }
}
```

### M-3: No Minimum Vesting Percentage
**Severity**: LOW-MEDIUM - Edge case  
**Location**: `BondingCurvePool.sol` constructor

**The Issue**:
```solidity
require(_reservedPercentage <= 25, "Vesting exceeds 25%");
```

But there's no minimum! Someone could create a "PRO token" with 1% vesting, which results in:
- Curve: 74%
- Vesting: 1% (split into 3 contracts with tiny amounts)
- LP: 25%

This works technically, but is it intended? Very small vesting amounts (< 1% of supply) may not be worth the gas cost.

**Consider**:
```solidity
require(_reservedPercentage == 0 || _reservedPercentage >= 5, "Min 5% vesting for PRO tokens");
```

Or document that 1% vesting is acceptable.
