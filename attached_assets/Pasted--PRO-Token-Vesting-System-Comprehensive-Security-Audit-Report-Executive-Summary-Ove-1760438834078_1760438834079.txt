## 🚨 NEW CRITICAL ISSUES (Introduced by Changes)

### NC-1: `reserveDistributed` Flag Logic Broken 🔴 CRITICAL
**Severity**: CRITICAL  
**Impact**: Creator can bypass vesting and steal tokens

**The Bug**:
```solidity
// In transferReserveToVesting()
function transferReserveToVesting(address vestingContract, uint256 amount) external nonReentrant {
    require(msg.sender == factory, "Only factory can transfer to vesting");
    require(!reserveDistributed, "Reserve already distributed");  // ❌ Checks flag
    
    // ... transfer logic ...
    
    // ❌ NEVER SETS THE FLAG!
    // Missing: reserveDistributed = true;
}
```

**Attack Scenario**:
1. User creates PRO token with 20% reserve, allocates 100% to vesting
2. TokenFactory calls `transferReserveToVesting()` 3 times, transferring all 20%
3. `reserveDistributed` is still `false` (flag never set)
4. Creator calls `distributeReserve([evilWallet], [dustAmount])`
5. Check passes: `!reserveDistributed == true` ✓
6. Creator steals any dust tokens left in contract

**Why This Happens**:
The flag is checked but never set because the function needs to be called 3 times (once per vesting contract). If it was set on the first call, the second would fail.

**Fix Option A** (Recommended): Add finalization function
```solidity
// In BondingCurvePool.sol
bool public vestingInitialized; // New flag

function transferReserveToVesting(address vestingContract, uint256 amount) external nonReentrant {
    require(msg.sender == factory, "Only factory can transfer to vesting");
    require(!reserveDistributed && !vestingInitialized, "Reserve already allocated");
    
    uint256 availableReserve = balanceOf(address(this)) - virtualTokenReserve;
    require(amount <= availableReserve, "Exceeds available reserve");
    
    isVestingContract[vestingContract] = true;
    _transfer(address(this), vestingContract, amount);
}

function finalizeVestingSetup() external {
    require(msg.sender == factory, "Only factory");
    require(!vestingInitialized, "Already finalized");
    vestingInitialized = true;
    reserveDistributed = true; // Also mark as distributed
}

// Update distributeReserve guard
function distributeReserve(...) external nonReentrant {
    require(reservedPercentage > 0, "BASIC token has no reserve");
    require(!vestingInitialized, "Vesting already set up"); // ✅ Can't bypass vesting
    require(!reserveDistributed, "Reserve already distributed");
    // ... rest of function
}
```

**Fix Option B**: Remove `!reserveDistributed` check from `transferReserveToVesting()` and rely on `availableReserve` check only. But this allows creator to call `distributeReserve()` even after partial vesting setup.

**Recommendation**: Use Fix Option A with separate `vestingInitialized` flag.

### NC-2: Graduation Liquidity Miscalculation 🔴 CRITICAL
**Severity**: CRITICAL  
**Impact**: DEX pools may have 0% liquidity, breaking graduation

**The Issue**:
Original model promises: **75% curve + 25% LP**

But with vesting:
- 75% goes to curve ✓
- Up to 25% goes to reserve (for vesting OR LP)
- If 100% of reserve is vested → **75% curve + 0% LP** ❌

**Current Code**:
```solidity
function initiateGraduation() external nonReentrant {
    // ...
    uint256 contractBalance = balanceOf(address(this));
    uint256 actualLpTokens = contractBalance - virtualTokenReserve;
    // If all reserve tokens went to vesting, actualLpTokens ≈ 0!
}
```

**Economic Impact**:
| Reserve | Vested | LP Available | DEX Liquidity |
|---------|--------|--------------|---------------|
| 25% | 0% | 25% | ✅ Good |
| 25% | 10% | 15% | ✅ Okay |
| 25% | 20% | 5% | ⚠️ Thin |
| 25% | 25% | 0% | ❌ **BROKEN** |

A token that vests 100% of its reserve will graduate with **ZERO liquidity** on the DEX. This breaks the entire graduation mechanism.

**Fix**: Require minimum LP percentage
```solidity
// In TokenFactory.createToken()
if (reservedPercentage > 0) {
    require(
        airdropsAllocation + marketingAllocation + teamAllocation == 100,
        "Allocations must sum to 100%"
    );
    
    // ✅ NEW: Enforce minimum LP liquidity
    uint256 totalVestedPct = (reservedPercentage * (airdropsAllocation + marketingAllocation + teamAllocation)) / 100;
    uint256 lpPct = reservedPercentage - totalVestedPct;
    
    require(lpPct >= 5, "Minimum 5% must go to LP for graduation");
    // This means if reserve is 25%, max 20% can be vested
}
```

**Alternative Fix**: Clearly document in UI that vested reserve reduces LP liquidity, and show warning:
```javascript
// In frontend
const lpPercentage = reservedPercentage - (reservedPercentage * totalVestedPercent / 100);
if (lpPercentage < 5) {
    showWarning("Low graduation liquidity! Only " + lpPercentage + "% will go to DEX.");
}
```

**Recommendation**: Use both fixes - enforce minimum AND warn users.

### NC-3: Missing Token Transfer Validation 🟡 HIGH
**Severity**: HIGH  
**Impact**: Silent failures if token transfer to vesting fails

**The Issue**:
```solidity
// In TokenFactory.createToken()
pool.transferReserveToVesting(airdropVestingAddress, airdropTokens);
pool.transferReserveToVesting(marketingVestingAddress, marketingTokens);
pool.transferReserveToVesting(teamVestingAddress, teamTokens);

// ❌ No verification that tokens were actually received!
```

If `transferReserveToVesting()` reverts, the entire `createToken()` transaction fails (which is good). But if it succeeds but transfers 0 tokens due to a bug, there's no check.

**Fix**: Add balance verification
```solidity
// In TokenFactory.createToken()
if (airdropTokens > 0) {
    AirdropVesting av = new AirdropVesting(...);
    airdropVestingAddress = address(av);
    
    pool.transferReserveToVesting(airdropVestingAddress, airdropTokens);
    
    // ✅ Verify tokens received
    require(
        IERC20(poolAddress).balanceOf(airdropVestingAddress) == airdropTokens,
        "Airdrop vesting underfunded"
    );
}
```

**Fix Option B**: Two-step beneficiary change (safer)
```solidity
address public proposedBeneficiary;
uint256 public proposalTimestamp;

function proposeBeneficiaryChange(address newBeneficiary) external {
    require(msg.sender == beneficiary, "Only current beneficiary");
    proposedBeneficiary = newBeneficiary;
    proposalTimestamp = block.timestamp;
}

function acceptBeneficiaryChange() external {
    require(msg.sender == proposedBeneficiary, "Only proposed beneficiary");
    require(block.timestamp >= proposalTimestamp + 7 days, "7 day timelock");
    beneficiary = proposedBeneficiary;
```

### M-5: No Partial Withdrawal Gas Optimization
**Issue**: Beneficiary must withdraw ALL unlocked tokens, can't do partial withdrawals

**Current**:
```solidity
function withdraw() external nonReentrant {
    uint256 amount = getWithdrawableAmount();
    require(amount > 0, "Nothing to withdraw");
    // Withdraws EVERYTHING unlocked
}
```

**Better**:
```solidity
function withdraw(uint256 amount) external nonReentrant {
    uint256 available = getWithdrawableAmount();
    require(amount > 0 && amount <= available, "Invalid amount");
    
    withdrawn += amount;
    require(token.transfer(beneficiary, amount), "Transfer failed");
}
```

**Benefit**: Allows dollar-cost averaging, gas optimization for small withdrawals

**Recommendation**: Nice-to-have, not critical.
