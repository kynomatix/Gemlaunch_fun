### M-2: Team Members Don't Control Their Vesting
**Severity**: MEDIUM - Design limitation  
**Location**: Automatic beneficiaries (team → msg.sender)

**The Problem**: 
Team vesting goes to **creator's wallet**, not individual team members. This means:
1. Team members don't directly control their vested tokens
2. Creator must manually distribute after claiming
3. Trust dependency (team trusts creator to distribute fairly)

**Example Scenario**:
```
Token created with 25% vesting:
- 10% Team allocation → 100M tokens
- Beneficiary: Creator wallet (0xCREATOR)

Team has 5 members who should get 20M each.

Month 12 (halfway through vesting):
- 50M tokens unlocked in CliffVesting contract
- Creator calls withdraw() → 50M goes to creator wallet
- Creator must manually send 10M to each team member
- What if creator doesn't? Tokens stuck in creator wallet!
```

**Is This a Bug?** No, it's intentional design per the spec: "Creators can manually transfer tokens later (more txs = better chain stats!)"

**Recommendation**: Add prominent warning in UI:
```
⚠️ WARNING: Team Vesting Tokens
Team tokens will vest to YOUR wallet (the token creator).
You are responsible for manually distributing tokens to your team members.
Team members will NOT receive tokens automatically.
```

### M-3: No Emergency Pause for Vesting Contracts
**Severity**: MEDIUM - No recovery mechanism  
**Location**: All vesting contracts

**The Problem**: Vesting contracts are 100% immutable:
- No pause function
- No admin
- No emergency stop

**Scenarios Where This Could Be Problematic**:
1. **Bug Discovery**: If a critical bug is found in vesting contract after deployment, no way to pause
2. **Beneficiary Compromise**: If creator's wallet is hacked, attacker can claim all vested tokens
3. **Legal Issues**: If legal dispute requires freezing tokens, blockchain can't comply

**Is This a Bug?** No, it's intentional for maximum trustlessness.

**Trade-off**: 
- ✅ Maximum security (no admin can rug)
- ❌ No recovery if things go wrong

**Recommendation**: Document this clearly:
```
⚠️ Vesting Contracts Are Immutable
- Cannot be paused or stopped
- Cannot change beneficiary
- No admin backdoors
- Tokens vest automatically based on time
- If you lose wallet access, tokens are PERMANENTLY LOST
```

### L-4: Missing Validation in AirdropVesting
**Severity**: LOW - Edge case protection  
**Location**: AirdropVesting.sol getUnlockedAmount()

**Potential Issue**:
```solidity
uint256 daysElapsed = elapsed / 1 days;
uint256 unlocked = (totalAllocation * daysElapsed * DAILY_UNLOCK_PCT) / 100;

return unlocked > totalAllocation ? totalAllocation : unlocked;
```

**Edge Case**: If `totalAllocation` is very small (< 100 tokens) and `daysElapsed` is large:
- Day 1: unlocked = (50 * 1 * 5) / 100 = 2 tokens ✓
- Day 20: unlocked = (50 * 20 * 5) / 100 = 50 tokens ✓
- Works fine!

But if `totalAllocation` is 1 token:
- Day 1: unlocked = (1 * 1 * 5) / 100 = 0 tokens (truncated)
- Day 20: unlocked = (1 * 20 * 5) / 100 = 1 token ✓

User would have to wait until day 20 to get their 1 token. Not ideal, but edge case is unlikely (smallest realistic allocation is thousands of tokens).

**Recommendation**: Add minimum allocation check in TokenFactory:
```solidity
require(airdropTokens >= 100 * 10**18, "Airdrop allocation too small");
require(marketingTokens >= 100 * 10**18, "Marketing allocation too small");
require(teamTokens >= 100 * 10**18, "Team allocation too small");
```

This ensures daily unlocks are meaningful (minimum 5 tokens/day for airdrops).
