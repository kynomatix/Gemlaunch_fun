## 🟡 **NEW ISSUES FOUND**

### N-1: VestingManager Constructor Not Called in Old Code Path
**Severity**: MEDIUM - Potential deployment issue  
**Location**: `TokenFactory.sol` constructor line 101

**The Issue**:
In the constructor, VestingManager is deployed with:
```solidity
// C-1 FIX: Deploy VestingManager with access control
VestingManager vm = new VestingManager(address(this));
vestingManager = address(vm);
```

But the original constructor parameters show:
```solidity
constructor(
    // ... 9 other parameters
    address _vestingManager  // ← This parameter exists!
) Ownable(msg.sender) {
```

**This creates ambiguity**: Is VestingManager deployed by factory, or passed as a parameter? The code does both:
1. Accepts `_vestingManager` parameter
2. Deploys new VestingManager internally
3. Ignores the `_vestingManager` parameter completely

**Fix** - Choose one approach:

**Option 1** (Recommended - Factory deploys):
```solidity
constructor(
    address _graduationController,
    address _treasury,
    address _airdropTreasury,
    address _platformDevelopmentWallet,
    address _graduationOracle,
    address _admin,
    address _buybackReserve,
    address _kaspaSupport,
    address _communityRewards
    // ✅ REMOVE: address _vestingManager parameter
) Ownable(msg.sender) {
    // ... validations
    
    // Deploy VestingManager (factory controls it)
    VestingManager vm = new VestingManager(address(this));
    vestingManager = address(vm);
}
```

**Option 2** (External deployment):
```solidity
constructor(
    // ... 9 parameters
    address _vestingManager
) Ownable(msg.sender) {
    require(_vestingManager != address(0), "Bad vesting");
    
    // ... other validations
    
    // Use external VestingManager (must be pre-deployed with correct factory address)
    vestingManager = _vestingManager;
    
    // Verify it's correctly configured
    require(VestingManager(_vestingManager).factory() == address(this), "Wrong factory");
}
```

**Recommendation**: Use Option 1 (factory deploys). This ensures VestingManager is always correctly configured with factory address.

### N-2: Integer Overflow Risk in Total Allocations Check
**Severity**: LOW - Edge case protection  
**Location**: `TokenFactory.sol` line 129

**The Issue**:
```solidity
uint256 totalAllocations = uint256(airdropsAllocation) + uint256(marketingAllocation) + uint256(teamAllocation);
require(totalAllocations == 100, "Allocations must sum to exactly 100%");
```

If someone passes `airdropsAllocation = 255, marketingAllocation = 255, teamAllocation = 255` (max uint8 values):
- `totalAllocations = 765`
- Check fails ✅ (correct behavior)

But if they pass values that sum to exactly 256:
- `totalAllocations = 256` (wraps to 0 in uint8, but we cast to uint256 so no wrap)
- Check fails ✅ (correct behavior)

**Actually this is SAFE** because we cast to uint256 before adding. No overflow possible.

**But for clarity**, add bounds check:
```solidity
require(airdropsAllocation <= 100, "Airdrop allocation > 100%");
require(marketingAllocation <= 100, "Marketing allocation > 100%");
require(teamAllocation <= 100, "Team allocation > 100%");
uint256 totalAllocations = uint256(airdropsAllocation) + uint256(marketingAllocation) + uint256(teamAllocation);
require(totalAllocations == 100, "Allocations must sum to exactly 100%");
```

This makes the intent clearer and fails faster with better error messages.

### N-3: VestingManager Doesn't Validate Factory Address
**Severity**: LOW - Deployment safety  
**Location**: `VestingManager.sol` constructor line 13

**The Issue**:
```solidity
constructor(address _factory) {
    require(_factory != address(0), "Invalid factory address");
    factory = _factory;
}
```

This only checks for zero address. But what if someone accidentally passes a random address?

**Better validation**:
```solidity
constructor(address _factory) {
    require(_factory != address(0), "Invalid factory address");
    
    // Verify factory is a contract (has code)
    uint256 codeSize;
    assembly {
        codeSize := extcodesize(_factory)
    }
    require(codeSize > 0, "Factory must be a contract");
    
    factory = _factory;
}
```

This prevents accidentally setting factory to an EOA (externally owned account) which would brick the VestingManager.

### N-4: Missing Event Emission in VestingManager
**Severity**: LOW - Monitoring gap  
**Location**: `VestingManager.sol` deployVestingContracts()

**The Issue**:
When vesting contracts are deployed, there's no event emitted by VestingManager itself. Only TokenFactory emits `VestingDeployed`.

**Add event**:
```solidity
event VestingContractsDeployed(
    address indexed pool,
    address airdropVesting,
    address marketingVesting,
    address teamVesting,
    uint256 airdropTokens,
    uint256 marketingTokens,
    uint256 teamTokens
);

function deployVestingContracts(...) external returns (VestingContracts memory result) {
    // ... existing code
    
    emit VestingContractsDeployed(
        poolAddress,
        result.airdropVesting,
        result.marketingVesting,
        result.teamVesting,
        result.airdropTokens,
        result.marketingTokens,
        result.teamTokens
    );
    
    return result;
}
```

This makes it easier to track vesting deployments directly from VestingManager.
