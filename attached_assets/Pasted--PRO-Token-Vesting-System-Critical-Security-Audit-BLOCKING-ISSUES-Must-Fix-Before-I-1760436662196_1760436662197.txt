# PRO Token Vesting System - Critical Security Audit

## 🔴 **BLOCKING ISSUES** (Must Fix Before Implementation)

### BI-1: Token Transfer Mechanism is Broken
**Severity**: CRITICAL - Vesting system will not work  
**Location**: TokenFactory specification, token transfer to vesting contracts

**The Problem**:
```solidity
// ❌ THIS WILL FAIL
IERC20(poolAddress).transferFrom(poolAddress, airdropVesting, airdropTokens);
```

**Why It Fails**:
- `transferFrom(A, B, amount)` requires A to approve the caller
- Pool contract never approved TokenFactory
- Even if it did, pool can't approve itself to spend its own tokens
- Transaction will revert with "ERC20: insufficient allowance"

**Correct Solution - Option 1 (Recommended)**:
```solidity
// In TokenFactory.createToken()
BondingCurvePool pool = new BondingCurvePool(...);
address poolAddress = address(pool);

// Deploy vesting contracts
AirdropVesting av = new AirdropVesting(...);

// Transfer tokens FROM pool TO vesting contract
// Pool needs a special function for this:
pool.transferReserveToVesting(address(av), airdropTokens);
```

**Add to BondingCurvePool.sol**:
```solidity
address public factory; // Set in constructor

function transferReserveToVesting(address vestingContract, uint256 amount) external {
    require(msg.sender == factory, "Only factory");
    require(!reserveDistributed, "Reserve already distributed");
    
    uint256 availableReserve = balanceOf(address(this)) - virtualTokenReserve;
    require(amount <= availableReserve, "Exceeds available reserve");
    
    _transfer(address(this), vestingContract, amount);
}
```

### BI-3: Wallet Cap Exemption Missing for Vesting Contracts
**Severity**: HIGH - Vesting contracts can't receive tokens > 10%  
**Location**: BondingCurvePool.sol `_update()` function

**The Problem**:
If reserve is 25% and all goes to one vesting contract, that's 25% of total supply. But wallet cap is 10%. Transfer will revert.

**Current Exemptions**:
```solidity
function _update(address from, address to, uint256 amount) internal virtual override {
    if (to != address(0) &&
        to != address(this) && 
        to != airdropTreasury &&  // ✅ Exempt
        to != graduationOracle &&
        to != owner() &&
        from != airdropTreasury &&
        from != address(this) &&
        !graduated) {
        // Enforce 10% cap
    }
}
```

**Problem**: Vesting contracts are NOT in this exemption list.

**But There's a Deeper Issue**: How does the pool know which addresses are vesting contracts? They're deployed AFTER the pool is deployed.

**Solution - Option 1 (Registry Approach)**:
```solidity
mapping(address => bool) public isVestingContract;

function registerVestingContract(address vestingContract) external {
    require(msg.sender == factory, "Only factory");
    isVestingContract[vestingContract] = true;
}

function _update(address from, address to, uint256 amount) internal virtual override {
    if (to != address(0) &&
        to != address(this) && 
        to != airdropTreasury &&
        to != graduationOracle &&
        to != owner() &&
        from != airdropTreasury &&
        from != address(this) &&
        !isVestingContract[to] &&  // ✅ Exempt vesting contracts
        !graduated) {
        // Enforce 10% cap
    }
}
```

**Solution - Option 2 (Simpler - Exempt All Factory Transfers)**:
```solidity
address public factory; // Set in constructor

function _update(address from, address to, uint256 amount) internal virtual override {
    // Bypass cap for factory transfers (only happens during deployment)
    if (from == factory) {
        super._update(from, to, amount);
        return;
    }
    
    // Enforce cap for normal transfers
    if (to != address(0) && /* existing exemptions */ !graduated) {
        uint256 maxWallet = totalSupply() * MAX_WALLET_PCT / 100;
        require(balanceOf(to) + amount <= maxWallet, "Exceeds max wallet");
    }
    
    super._update(from, to, amount);
}
```

### BI-4: Vesting Contract Beneficiary Can Bypass Vesting via Ownership Transfer
**Severity**: HIGH - Security vulnerability  
**Location**: All vesting contracts inherit `Ownable`

**The Problem**:
```solidity
contract AirdropVesting is Ownable {
    address public immutable beneficiary;
    
    function withdraw() external {
        require(msg.sender == beneficiary, "Only beneficiary");
        // ...
    }
}
```

The contract inherits `Ownable(msg.sender)` making the factory the owner. If ownership is transferred, the new owner could call any admin functions. Even worse: if `beneficiary` is mutable, owner could change it.

**Attack Vector**:
1. Creator deploys PRO token with team vesting
2. Team member is beneficiary
3. If owner transfers ownership to team member
4. Team member could potentially manipulate contract

**Fix**: Make beneficiary immutable and remove `Ownable`:
```solidity
contract AirdropVesting {  // Remove Ownable inheritance
    IERC20 public immutable token;
    address public immutable beneficiary;  // Already immutable ✅
    uint256 public immutable totalAllocation;
    uint256 public immutable startTime;
    uint256 public constant DAILY_UNLOCK_PCT = 5;
    uint256 public constant VESTING_PERIOD = 20 days;
    uint256 public withdrawn;
    
    constructor(
        address _token,
        address _beneficiary,
        uint256 _totalAllocation
    ) {  // Remove Ownable(msg.sender)
        token = IERC20(_token);
        beneficiary = _beneficiary;
        totalAllocation = _totalAllocation;
        startTime = block.timestamp;
    }
    
    // No owner, no ownership transfer, fully immutable
}
```

### H-2: Graduation Approval Amount Incorrect for Variable Reserve
**Severity**: HIGH - DEX migration could fail  
**Location**: `initiateGraduation()` function

**Current Code**:
```solidity
function initiateGraduation() external nonReentrant {
    // ...
    uint256 lpTokens = totalSupply() * LP_SUPPLY_PCT / 100; // ❌ Hardcoded
    
    _approve(address(this), graduationOracle, lpTokens);
    // ...
}
```

**With Variable Reserve**:
If reservedPercentage = 10%, then lpTokens = 10% of supply (not 25%)

**But what if reserve was already distributed?**
```solidity
// Creator called distributeReserve() and sent all 10% to team
// Contract no longer has 10% reserve tokens
// Graduation tries to approve 10% that doesn't exist
```

**Fix**:
```solidity
function initiateGraduation() external nonReentrant {
    require(msg.sender == graduationOracle, "Only oracle");
    require(!graduated && !graduating, "Already graduated");
    
    graduating = true;
    
    // ✅ Calculate actual LP tokens available (not theoretical reserve)
    uint256 contractBalance = balanceOf(address(this));
    uint256 actualLpTokens = contractBalance - virtualTokenReserve;
    
    require(actualLpTokens > 0, "No LP tokens available");
    
    _approve(address(this), graduationOracle, actualLpTokens);
    
    // Transfer KAS
    uint256 actualKasLiquidity = virtualKasReserve - INITIAL_VIRTUAL_KAS;
    _safeSend(graduationOracle, actualKasLiquidity);
    liquidityTransferred = true;
    
    emit GraduationInitiated(virtualKasReserve, actualLpTokens);
}
```

### H-3: Vesting Contract Reentrancy Risk on withdraw()
**Severity**: HIGH - Potential reentrancy attack  
**Location**: All vesting contracts

**Current Code**:
```solidity
function withdraw() external {
    require(msg.sender == beneficiary, "Only beneficiary");
    
    uint256 amount = getWithdrawableAmount();
    require(amount > 0, "Nothing to withdraw");
    
    withdrawn += amount;  // ✅ State updated before transfer (CEI pattern)
    require(token.transfer(beneficiary, amount), "Transfer failed");  // ✅ External call last
}
```

**Actually this is CORRECT** - follows Checks-Effects-Interactions (CEI) pattern. State is updated before external call.

**But Missing**: No ReentrancyGuard.

**Fix - Add ReentrancyGuard**:
```solidity
import "@openzeppelin/contracts/utils/ReentrancyGuard.sol";

contract AirdropVesting is ReentrancyGuard {  // Add inheritance
    // ...
    
    function withdraw() external nonReentrant {  // Add modifier
        require(msg.sender == beneficiary, "Only beneficiary");
        
        uint256 amount = getWithdrawableAmount();
        require(amount > 0, "Nothing to withdraw");
        
        withdrawn += amount;
        require(token.transfer(beneficiary, amount), "Transfer failed");
    }
}
```

### M-2: Vesting Start Time Edge Case
**Severity**: MEDIUM - Time manipulation risk  
**Location**: All vesting contracts

**The Issue**:
```solidity
constructor(...) {
    startTime = block.timestamp;  // Set to deployment time
}
```

**Problem**: If TokenFactory deployment transaction is delayed (network congestion), `startTime` could be much later than user expects.

**Example**:
- User submits transaction at 10:00 AM
- Network congested, mined at 10:30 AM
- Vesting starts at 10:30 AM (not 10:00 AM)
- 30-minute discrepancy

**Fix - Allow Configurable Start Time**:
```solidity
constructor(
    address _token,
    address _beneficiary,
    uint256 _totalAllocation,
    uint256 _startTime  // NEW: Allow future start time
) {
    token = IERC20(_token);
    beneficiary = _beneficiary;
    totalAllocation = _totalAllocation;
    
    // If _startTime is 0 or in past, use current time
    startTime = _startTime > block.timestamp ? _startTime : block.timestamp;
}
```

But this adds complexity. **Recommendation**: Keep it simple, accept block.timestamp, document this behavior.

### M-4: Vesting Contract Has No Emergency Recovery
**Severity**: MEDIUM - Tokens could be stuck  
**Location**: All vesting contracts

**The Problem**:
```solidity
contract AirdropVesting {
    // No owner, no admin, no emergency functions
    // If beneficiary loses private key → tokens locked forever
}
```

**Scenarios**:
1. Beneficiary loses wallet access
2. Beneficiary dies (no inheritance mechanism)
3. Beneficiary's wallet is compromised (can't stop attacker)

**Recommendation**: Add time-delayed recovery mechanism:
```solidity
address public recoveryAddress;
uint256 public recoveryActivationTime;
uint256 public constant RECOVERY_DELAY = 365 days; // 1 year

function initiateRecovery(address newBeneficiary) external {
    require(msg.sender == /* some admin or DAO */, "Unauthorized");
    recoveryAddress = newBeneficiary;
    recoveryActivationTime = block.timestamp + RECOVERY_DELAY;
}

function executeRecovery() external {
    require(block.timestamp >= recoveryActivationTime, "Recovery not ready");
    require(recoveryAddress != address(0), "No recovery initiated");
    
    beneficiary = recoveryAddress;
    recoveryAddress = address(0);
}

function cancelRecovery() external {
    require(msg.sender == beneficiary, "Only beneficiary");
    recoveryAddress = address(0);
}
```

But this contradicts "fully immutable" goal. **Trade-off decision needed.**

## 🔵 **LOW SEVERITY / OPTIMIZATION**

### L-1: Vesting Math Could Overflow in Edge Cases
**Severity**: LOW - Solidity ^0.8.20 has overflow protection  
**Location**: Vesting calculation functions

**Example**:
```solidity
// In LinearVesting
function getUnlockedAmount() public view returns (uint256) {
    uint256 elapsed = block.timestamp - startTime;
    if (elapsed >= duration) return totalAllocation;
    
    return (totalAllocation * elapsed) / duration;  // Could overflow if totalAllocation is huge
}
```

**With Solidity ^0.8.20**: Overflow causes revert (safe).

**But Better**: Add explicit checks:
```solidity
function getUnlockedAmount() public view returns (uint256) {
    uint256 elapsed = block.timestamp - startTime;
    if (elapsed >= duration) return totalAllocation;
    
    // Prevent overflow: Check if multiplication would overflow
    if (totalAllocation > type(uint256).max / elapsed) {
        // If would overflow, return proportional result using different math
        return (totalAllocation / duration) * elapsed;
    }
    
    return (totalAllocation * elapsed) / duration;
}
```
